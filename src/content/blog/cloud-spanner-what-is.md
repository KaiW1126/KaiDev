## はじめに

Cloud SpannerはGoogle Cloudが提供するフルマネージドの**分散リレーショナルデータベース**です。

SQLとトランザクションを使えるRDBの使い勝手を保ちつつデータを複数のサーバーやリージョンへ分散できます。大規模なECサイトで在庫と注文を正しく扱うようなシステムで力を発揮します。こうしたシステムではアクセス量・可用性・データ整合性を同時に求められます。

この記事ではCloud Spannerが何を解決するサービスなのかを押さえます。そのうえでデータを分割しても間違いなく提供できる仕組みを見ていきます。

---

## Cloud SpannerはRDBではないのか？

Cloud SpannerはRDBと対立するものではありません。**Spanner自体が分散RDB**です。

RDBはテーブル・主キー・SQL・トランザクションといったデータモデルや操作方法を指します。一方でSpannerはそのRDBを最初から複数マシン・複数リージョンで動かせるように設計したサービスです。

この性質からSpannerは一般に**分散SQL**または**NewSQL**に分類されます。Googleの公式資料では主に「分散SQLデータベース」という表現が使われています。

| サービス      | データモデル          | 主なスケーリングの考え方             | 向く用途                                             |
| ------------- | --------------------- | ------------------------------------ | ---------------------------------------------------- |
| Cloud SQL     | RDB                   | インスタンスの拡張や読み取りレプリカ | 一般的なWebアプリ、既存のMySQL・PostgreSQL資産の活用 |
| Cloud Spanner | 分散RDB               | 書き込みも含めた自動分割・分散       | グローバルな基幹システム、注文・在庫・決済           |
| Bigtable      | NoSQLのワイドカラムDB | 大量データの高スループット処理       | 時系列データ、ログ、IoTデータ                        |

Cloud SQLも高可用構成や読み取りレプリカを利用できます。ただし書き込みまで大きく水平分散する場合はデータの分割や整合性をアプリケーション側で考える場面が増えます。Spannerではその難しい部分をDB側が担います。

**参考資料**：[Spanner documentation | Google Cloud](https://cloud.google.com/spanner/docs) / [Cloud SQL documentation | Google Cloud](https://cloud.google.com/sql/docs) / [Bigtable documentation | Google Cloud](https://cloud.google.com/bigtable/docs)

## 水平スケーリングで本当に難しいこと

データを複数サーバーに分けること自体は難しくありません。難しいのは分けた後も正しいデータを返し続けることです。

- どのサーバーがどのデータを持つのか
- リクエストを正しいサーバーへどう届けるのか
- 同じデータを複数箇所に持つ場合にどのコピーを正とするのか
- 障害で一部のサーバーが落ちても古いデータを返さないようにできるか
- 複数サーバーにまたがる更新をまとめて成功または失敗させられるか

たとえばECサイトで在庫を減らして注文を作る処理を考えます。在庫テーブルと注文テーブルが別のサーバーに置かれていても「在庫だけ減って注文が作られない」状態は避けなければなりません。

Spannerはデータの分割・複製・合意・分散トランザクションを一体として扱うことでこの問題を解決しています。

**参考資料**：[Life of Spanner Reads & Writes | Google Cloud](https://cloud.google.com/spanner/docs/whitepapers/life-of-reads-and-writes)

## 1. データをSplitへ自動分割する

Spannerはテーブルのデータを**主キー順**に並べます。そして連続した主キー範囲ごとに**Split**へ分けます。

```text
Products テーブル（主キー: product_id）

Split A                 Split B                 Split C
0001 〜 3499            3500 〜 6999            7000 〜 9999
┌────────────┐          ┌────────────┐          ┌────────────┐
│ 商品 0001  │          │ 商品 4500  │          │ 商品 8001  │
│ 商品 0002  │          │ 商品 4501  │          │ 商品 8002  │
│    ...     │          │    ...     │          │    ...     │
└────────────┘          └────────────┘          └────────────┘
```

この範囲は固定ではありません。Spannerはデータ量や負荷に応じてSplitを分割・移動します。そして複数マシンに再配置します。アプリケーションは「商品4500はどのサーバーか」を持つ必要がありません。Spannerが主キーから対象のSplitを見つけて内部的にリクエストを振り分けます。

ここで主キー設計が重要になります。作成時刻のように単調に増える値を主キーの先頭にすると新しいデータが同じ主キー範囲へ集中します。Splitを増やしても書き込み先が偏る**ホットスポット**が起きるためです。

**参考資料**：[Life of Spanner Reads & Writes | Google Cloud](https://cloud.google.com/spanner/docs/whitepapers/life-of-reads-and-writes) / [Schema design best practices | Google Cloud](https://cloud.google.com/spanner/docs/schema-design)

## 2. Splitを複数の障害ドメインへ複製する

Splitを分けるだけではそのサーバーが落ちたときにデータを失います。そこでSpannerは各Splitを複数の障害ドメインへ複製します。

```text
商品4500を含む Split B

                ┌─────────────────────┐
                │ Split B のデータ    │
                └──────────┬──────────┘
                           │ 複製
          ┌────────────────┼────────────────┐
          ▼                ▼                ▼
  ゾーン1のレプリカ  ゾーン2のレプリカ  ゾーン3のレプリカ
      Leader             Replica            Replica
```

ここで「すべてのサーバーがDB全体を持つ」と考える必要はありません。**各サーバーが担当するのは一部のSplit**です。一方であるSplitのデータは複数のレプリカに持たれます。

リージョナル構成ではSpannerは別々の3ゾーンに読み書き可能なレプリカを保持します。マルチリージョン構成ではデータを複数リージョンへ複製できます。構成によって可用性・レイテンシ・コストのバランスが変わります。

**参考資料**：[Regional, dual-region, and multi-region configurations | Google Cloud](https://cloud.google.com/spanner/docs/instance-configurations)

## 3. Paxosで「どのコピーが正しいか」を決める

コピーが複数あるだけでは不十分です。同じ商品に同時に更新が来たときに各コピーが別々の順序で更新されるとデータが壊れます。

Spannerは各Splitの投票レプリカに対して**Paxos**という合意方式を使います。レプリカのうち1つが**Leader（リーダー）**として書き込み処理を主導します。

```text
商品4500の在庫を 3 → 2 に更新する場合

ECアプリ
   │
   ▼
Split B の Leader
   │  更新案を送る
   ├──────────────► レプリカ1: OK
   └──────────────► レプリカ2: OK

投票レプリカ3台のうち2台が同じ更新を記録
   │
   ▼
「在庫 2」としてコミットを確定
```

投票レプリカが3台なら2台の合意が多数派です。1台が障害中でも残り2台で確定できます。

一方で2台が同時に使えなくなれば多数派を作れません。この場合にSpannerは不確かな更新を確定するより整合性を優先します。Leaderが停止しても多数派が保持する確定済みの履歴を基に新しいLeaderを選出できます。

つまりSpannerが正しいデータを返せるのは「どこか1台のコピーを信じる」からではありません。**多数派が合意した更新履歴だけを確定済みとして扱う**からです。

**参考資料**：[Life of Spanner Reads & Writes | Google Cloud](https://cloud.google.com/spanner/docs/whitepapers/life-of-reads-and-writes) / [Spanner: Google’s Globally-Distributed Database | OSDI 2012](https://research.google.com/archive/spanner-osdi2012.pdf)

## 4. TrueTimeで更新の順序を世界規模でそろえる

Paxosによって1つのSplit内の更新順序は決められます。しかしSpannerは複数Splitや複数リージョンにまたがるトランザクションも扱います。

ここで使われるのが**TrueTime**です。分散環境ではサーバーごとの時計がわずかにずれます。各サーバーのローカル時刻だけでコミット時刻を決めると、先に完了した処理より後の処理が先に見える可能性があります。

SpannerはTrueTimeを使って時刻の不確実性を考慮したコミット時刻を決定します。これにより先に完了したトランザクションは後から始まったトランザクションより必ず先に観測されます。この性質を**外部整合性**と呼びます。

```text
時刻 ───────────────────────────────────►

注文A:  在庫を減らして注文を確定
        [開始────────コミット完了]

注文B:                           [開始────コミット]

利用者が見る順序: 注文A → 注文B
```

ECサイトで言えば購入者Aの注文完了後に購入者Bが在庫を確認したならBはAの在庫減少を反映した状態を読みます。注文Aが終わった後に商品がまだ在庫3個として見えることはありません。

**参考資料**：[TrueTime and external consistency | Google Cloud](https://cloud.google.com/spanner/docs/true-time-external-consistency)

## ECサイトの注文処理に当てはめる

在庫が残り1個の商品に2人が同時に注文したケースを考えます。

```text
トランザクションでまとめる処理

1. 商品4500の在庫を読む
2. 在庫が1以上なら、在庫を1減らす
3. 注文レコードを作る
4. まとめてコミットする
```

2つのトランザクションが競合した場合に両方が「残り1個」を確定することはありません。片方が先にコミットされます。もう片方は競合として中断されるためアプリケーションは安全に再試行できるよう実装します。

この例はSpannerの本質を理解するための補助です。重要なのは在庫と注文が別のSplitに分かれていてもSpannerが分散トランザクションとして一貫して扱える点です。

**参考資料**：[Transactions overview | Google Cloud](https://cloud.google.com/spanner/docs/transactions) / [Life of Spanner Reads & Writes | Google Cloud](https://cloud.google.com/spanner/docs/whitepapers/life-of-reads-and-writes)

## Spannerを使うことで得られることと残る設計

Spannerは水平スケーリングに伴う次の作業をサービス側で担います。

- データの自動分割と再配置
- リクエストの内部ルーティング
- 複数レプリカへの同期複製
- Leader選出とPaxosによる合意
- 複数Splitにまたがるトランザクション

ただしアプリケーション側の設計が不要になるわけではありません。

- ホットスポットを避ける主キー設計
- 検索と書き込みコストを踏まえたインデックス設計
- 競合による中断を想定したトランザクションのリトライ
- リージョン構成と書き込みレイテンシ・コストの判断

特にマルチリージョン構成の書き込みでは複数地点との合意が必要です。単一リージョンのDBより通信コストとレイテンシが増える可能性があります。Spannerは「何でも高速にするDB」ではなく**分散環境でも正しさを保つために必要なコストを引き受けるDB**です。

## まとめ

Cloud SpannerはSQLとトランザクションを使えるRDBをグローバルに水平スケールさせるための分散DBです。

データをSplitへ自動分割して負荷を分散します。各Splitを複製して障害に備えます。さらにPaxosとTrueTimeによって複数のコピーやリージョンにまたがっても矛盾しない更新順序を保証します。

そのためSpannerは注文・在庫・決済のように規模が大きくても不整合を許せないデータを扱うときに有力な選択肢になります。
